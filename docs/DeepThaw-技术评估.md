# DeepThaw 技术评估（对照本工具）

> 对象：[TimBlack422/DeepThaw](https://github.com/TimBlack422/DeepThaw)
> 结论先行：**它确实能做到"不重启、不进 PE 就解冻"，但代价是加载一个未签名内核驱动并在内核里改冰点的机器码。**
> 我没有把这条路搬进本工具，原因见第 6 节；但它有两个做法值得借鉴，已经落地（第 7 节）。

---

## 1. 它是什么

一个 C++ 的 Win32 程序，仓库里是**源码**（没有预编译的 exe），三个工程：

| 工程 | 作用 |
|---|---|
| `DeepThaw` | 用户态 GUI，负责识别产品、算偏移、发 IOCTL |
| `DeepThaw_Kernel` | **内核驱动**，真正干活的部分 |
| `DeepThaw_ForInjection` | 可注入的 DLL（用于挂进目标进程） |

支持范围（README 自述）：Deep Freeze Standard/Server/Enterprise 的多个具体 build、
Reboot Restore Rx、Rollback Rx、Shadow Defender。

## 2. 内核层怎么"解冻"的（按源码）

看 `DeepThaw_Kernel/Kernel_Interface_DeepFrz.cpp`，流程是：

1. **建自己的设备**：`\Device\DeepThaw_Kernel`，暴露两个控制码
   `IOCTL_DISABLE_DEEPFRZ_NORMAL` / `IOCTL_DISABLE_DEEPFRZ_FORCE`（见 `DriverControlCode.h`）。

2. **按名字拿到冰点的驱动对象**：`ReferenceDriverObjectByName(L"\\Driver\\DeepFrz", ...)`
   （另外还有 `FarSpace`，是冰点的另一个驱动）。

3. **改冰点驱动的导入表（IAT）**：
   用户态把 `ExSystemTimeToLocalTime` 在冰点驱动里的 RVA 通过 IOCTL 传进来；
   内核遍历 PE 导入表找到对应槽位，然后：
   ```c
   MmMapIoSpace(MmGetPhysicalAddress(pThunk), ...)   // 用物理地址映射绕过只读保护
   addrCanBeWritten->u1.Function = Hook_ExSystemTimeToLocalTime;
   ```
   —— 这是典型的"绕过写保护改内核内存"手法。

4. **在自己的 hook 里直接改调用方的机器码**：
   用 `RtlCaptureStackBackTrace` 回溯栈，算出冰点驱动里调用它的那条指令地址，
   改成 `B0 01 90 90 90`（`mov al,1; nop;nop;nop`），
   即让冰点内部"是否处于冻结/密码是否正确"的那个判断**返回 true**。
   Force 模式更狠：`RtlVirtualUnwind` 回溯后直接 `context.Rax = 1; RtlRestoreContext(...)` 强行返回。

5. **拦截写入**：`FSD_Hook.cpp` 注册了一个 minifilter，
   在"阻断开关"打开时把分页 I/O 写入吞掉（返回成功但写 0 字节），只放行 `\Windows\System32\config\SYSTEM`。
   配合 `IoBlock_Dispatch` 把 IRP 卡在事件上，让特定进程以外的人写不进去。

6. **关机时再来一次**：注册 `IoRegisterShutdownNotification`，卸载驱动前先把冰点再禁一遍，
   防止"关机时被重新冻结"。

一句话：**它不是在"卸载"冰点，而是在内核里把冰点的判断函数改成永远返回"已解冻"。**

## 3. 为什么它不用重启也能生效

因为它是"运行时打补丁"：驱动已经在内存里，它改的就是内存里的代码和数据，
不需要改硬盘上的任何东西，所以不受"冻结会还原"的影响。
—— 这一点和本工具的离线方案是**两种完全不同的思路**：
一个绕过过滤器的判断，一个干脆在过滤器不存在的环境里动手。

## 4. 要付的代价

| 代价 | 说明 |
|---|---|
| **必须编译** | 仓库只有源码，要 Visual Studio + WDK 自己编 |
| **未签名内核驱动** | Win10/11 x64 默认拒载。要关驱动签名强制（测试签名 / 启动时 F7 / 或 BYOVD 漏洞驱动），这几条本身都要额外的重启或高风险操作 |
| **版本强绑定** | README 把支持的 build 号一个个列出来了；冰点一更新就可能失效，甚至补丁打歪 → 蓝屏 |
| **蓝屏风险真实存在** | 作者自己在代码里写了注释："可能会蓝屏，如果 MmMapIoSpace 返回 0 的话。不过那不是我的问题了" |
| **杀软必报** | "物理内存映射改代码 + IAT hook + 拦 IRP"这三件套，是 EDR 眼里标准的 rootkit 行为，大概率直接被拦或直接隔离 |
| **只禁用，不卸载** | 它让冰点"失效"，但冰点还在系统里，服务、驱动、注册表都还在 |

## 5. 和我这个工具怎么配合（推荐工作流）

它的定位是"解冻器"，我的定位是"清理器"，两者其实**互补**：

```
DeepThaw（或其它方式）把冰点解冻
        ↓
本工具 DFRemover.ps1  →  [3] 在线强制卸载   （此时驱动不再保护，写入能落地）
        ↓
                    →  [4] 复查残留
```

也就是说：如果你已经用 DeepThaw 解冻成功，直接按 `3` 就行，不需要再进 PE。
本工具的 `[3]` 本来就是"只要求没被保护"，不关心你是怎么解冻的。

## 6. 我为什么不把它搬进本工具

1. **它会把我这个"绿色脚本"变成需要关驱动签名的东西。**
   本工具的全部价值是"拷过去就能跑、每一行都能看懂、不碰内核"。加一个未签名驱动，
   这两条全没了。
2. **风险和收益不成比例。**
   为了省一次重启，要承担：蓝屏、杀软拦截、版本失配、以及"以后每次系统更新都可能踩雷"。
   而 WinRE 方案只是多一次重启，成功率还更高。
3. **它做的事情本质上是在内核里改别人的代码。**
   这类技术我不适合替你打包分发——你自己编译、自己承担，和"我把它做进一个面向普通用户的工具"，性质不一样。

## 7. 从它身上借鉴了什么（已落地）

1. **"禁用"和"卸载"是两件事。**
   以前文档里没讲清，现在菜单 `[6]` 的提示里明确了：
   任何"解冻/禁用"手段（包括 DeepThaw）都只是让保护失效，**真正的清理还是要走卸载流程**。

2. **冰点之外还有别的"重启还原"软件。**
   它支持 Reboot Restore Rx / Rollback Rx / Shadow Defender，提醒了我：
   如果一台机器上装的不是冰点，本工具会报"未发现冰点"，用户就卡住了。
   现在扫描会**额外识别**这几类产品（只识别、不处理），并明确告诉你该另找方案。

## 8. 什么时候值得用它

- 机器**绝对不能重启**（有正在跑的业务、远程无人值守、重启就丢现场）；
- 你已经能编译并签名/加载内核驱动，且能接受杀软告警；
- 冰点版本正好落在它支持的 build 范围内。

其余情况，优先顺序建议是：
**有密码 → 官方卸载** ＞ **WinRE / 另一套系统** ＞ **U 盘 PE** ＞ **内核工具（DeepThaw 类）**。

## 9. 合规

- 只对你自己有管理权限的机器使用，两者都一样；
- 内核补丁类工具在受管环境（公司/学校/网吧）里属于绕过管理措施，
  可能违反使用协议甚至当地法规，自行判断。
